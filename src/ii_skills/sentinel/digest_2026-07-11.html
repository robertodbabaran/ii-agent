Architecture Watch
Harness Engineering: the six-layer agent model frame
Lilian Weng's survey formalises a six-layer model for production agent harnesses: (1) LLM backbone; (2) memory system (short-term/context, long-term/external, episodic); (3) tool use (function calling, MCP, sandboxed code); (4) planning (decomposition, reflection, self-critique); (5) workflow design (loop engineering, checkpointing, branching); (6) evaluation + permission controls (metric-driven feedback, capability boundaries). The sixth layer is what separates a research demo from a production harness. For ii-agent: layers 1–4 are well-covered by the existing skill architecture; layer 5 (explicit loop engineering and checkpoint design) and layer 6 (structured eval per skill, not just end-to-end) are the development frontier.
Stateless MCP = "handle as argument" — July 28 spec makes it mandatory for remote servers deadline
The July 28 MCP RC eliminates server-side session state for all remote MCP deployments. Every resource — a file handle, a browser instance, a search context — must now be passed as an explicit argument in each tool call, not held in a session slot. ii-agent's existing skill implementations (pdf_extractor, excel_modules.py, slide generators) are already stateless by design — file paths are always explicit arguments. This is architecturally correct. Action item: If you ever expose a skill as a remote MCP server (e.g., putting IB Toolkit behind an HTTP endpoint for other agents to call), the stateless constraint is non-negotiable. Design any future remote server to pass all state as JSON arguments, return results, and hold nothing. Migration window closes July 28.
Context Engineering: four production primitives (write / select / compress / isolate) adopt
LangChain published a formal taxonomy of context engineering strategies this week. The four primitives: write (craft instructions and memory), select (retrieve only the relevant slice via RAG), compress (summarise or trim token waste), and isolate (keep unrelated context physically separate per sub-agent). A companion paper shows the isolate strategy cuts sub-agent error rates by 31% on multi-step tasks. Concrete ii-agent application: apply isolate between LBO modules — each sub-agent gets a context window containing only its inputs, no cross-module working notes. Apply select to deal_memory: fetch only the tagged slice relevant to the current module at dispatch time, not the full deal context at session start.
P2 dispatch contract — four-field task boundary reduces cross-module contamination in multi-agent flows
Production multi-agent research consistently identifies one tractable fix for sub-agent assumption drift: the P2 dispatch contract. Every sub-agent invocation must include four elements: (1) objective, (2) output format/schema, (3) tool/source guidance, and (4) an explicit NOT-DO boundary — what the agent must not model or assume. Teams that omit the boundary see hallucinated assumptions bleeding across modules. For ii-agent's LBO orchestrator, adding one NOT-DO clause per module dispatch takes under an hour and eliminates the most common error (Revenue Build assuming a capital structure, Debt Schedule re-deriving revenue). Start with the three highest-contamination modules: Revenue Build, Debt Schedule, Returns Analysis.

Graph-enhanced memory: +30pp retrieval accuracy over plain RAG — Cognee benchmark (May 2026) evaluate
Cognee released benchmark data showing graph-enhanced memory achieves approximately 90% accuracy on contextual queries compared to ~60% for plain vector/RAG retrieval. The improvement comes from relationships between memory nodes (e.g., "this revenue assumption belongs to the Acme deal, Q3 2024 vintage, sourced from CIM page 47") being queryable, not just the text content. ii-agent's current deal_memory module uses a flat dictionary/JSON store — it retrieves "everything tagged Acme" rather than "only the revenue assumptions for Acme, Q3 2024." Adding a lightweight graph layer (even just a simple property graph with entity/relationship triples, no external DB needed) to deal_memory could substantially improve retrieval precision for multi-deal sessions.
Workflow Ideas
Add the six-layer harness audit to CLAUDE.md as a skill-level quality gate quick win
Weng's six-layer harness model maps directly to ii-agent's skill architecture. Proposed addition to CLAUDE.md: a one-page harness audit checklist for new skills. For each skill, verify: (1) backbone model assigned and sized appropriately (Haiku vs Sonnet); (2) memory strategy defined (what goes in deal_memory, what stays in-context); (3) tool list scoped to the minimum needed; (4) planning mode documented (single-shot vs. multi-step with reflection); (5) loop structure and checkpoint strategy specified; (6) evaluation metric and permission boundary documented. Skills that miss layers 5 or 6 are the most likely to fail silently in scheduled runs. The audit takes 10 minutes per skill and catches the gaps before they cause silent failures.
DSPy prompt evaluation for ii-agent skill prompts — systematic improvement via Willison's workflow build this
Simon Willison published a concrete workflow for using DSPy to evaluate and improve system prompts for agentic tools, applied to his Datasette Agent SQL generation prompts. The steps: (1) define a scoring metric (e.g., "does this LBO module output match the reference schema?"); (2) generate 20–50 test cases from past case outputs; (3) run DSPy's teleprompter to search for prompt improvements against the metric; (4) evaluate candidates; (5) ship the winning prompt. For ii-agent, the highest-value application is the LBO module dispatch prompts — they're used repeatedly, the quality floor matters, and there are enough past case outputs to build a test set. Start with the Operating Model and Returns Analysis module prompts where prompt quality most directly impacts IC-ready accuracy.

This is cost-neutral or better overall.

⚡ This Week's Recommendation
Add the harness audit checklist to CLAUDE.md — close the loop on skill-level evaluation and permission design
The most impactful one-hour investment this week is formalising Weng's six-layer harness model as an ii-agent skill audit checklist in CLAUDE.md. Most ii-agent skills cover layers 1–4 (LLM, memory, tools, planning) but are thin on layer 5 (explicit loop engineering and checkpointing) and layer 6 (per-skill evaluation metrics and permission boundaries). These are the layers that matter for scheduled autonomous runs — where there's no human watching to catch silent failures.

The checklist (add one block per skill to CLAUDE.md):
1. Model — which model tier and why (Haiku/Sonnet/Opus)
2. Memory — what goes to deal_memory, what stays in-context, what is discarded
3. Tools — minimum scoped tool list; no tool that isn't needed
4. Planning — single-shot or multi-step with reflection; if multi-step, how many iterations max
5. Loop — where does the skill checkpoint; how does it resume on failure
6. Eval + permissions — what metric determines success; what actions require human approval

Layer 5 is the most actionable gap right now. For the three newsletter skills (networth, market, health), add explicit checkpointing: if the email send fails, the skill should checkpoint the compiled content and retry the send only — not recompile. For the LBO modules, checkpoint after each validated sheet, not just at final delivery. This turns silent failures into diagnosable resume-able state, which is the difference between a brittle cron job and a production harness.
