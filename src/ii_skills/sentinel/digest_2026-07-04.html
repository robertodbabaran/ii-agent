02  MCP
MCP 2026-07-28 RC: the largest spec revision since launch — stateless by default, Tasks extension, MCP Apps, 24-day migration window
The release candidate for the July 28 MCP specification dropped this week and is described as "the largest revision since launch." The core structural change: sessions are eliminated. The initialize handshake and Mcp-Session-Id header are removed. Every request is now fully self-contained; servers run behind any load balancer without sticky sessions or shared session stores. State (file handles, search contexts, browser instances) becomes an explicit argument in each tool call — visible, auditable, and cacheable. New additions in the RC: Tasks extension for long-running work via opaque handles; MCP Apps for server-rendered UIs surfaced directly inside Claude Code; and routable headers (Mcp-Method, Mcp-Name) for gateway routing without body inspection. The ecosystem now indexes 15,930+ public MCP servers. The migration window closes July 28 — any ii-agent skill you plan to expose as an MCP server should be built stateless-first starting now.

Architecture Watch
Stateless MCP = "handle as argument" formalised at protocol level architecture
The 2026-07-28 RC enforces a clean design principle ii-agent's skill architecture already follows: every resource (Excel workbook, PDF, deal context) is a file-path argument, not a shared session object. The MCP spec now mandates this at protocol level for all remote servers. ii-agent's pdf_extractor, excel_modules.py, and slide generators are already stateless — the pattern is correct. The RC makes it the only legal pattern for remote servers. Any future skill you plan to expose as an MCP server: build stateless-first, pass all state as explicit arguments, return a result, hold nothing. Migration window closes July 28.
Context Engineering: write / select / compress / isolate are the four production primitives adopt
LangChain published a formal taxonomy of context engineering strategies this week. The four primitives: write (author instructions and memory), select (retrieve only the relevant slice via RAG), compress (summarise or truncate token waste), and isolate (keep unrelated context physically separate per sub-agent). A companion paper shows the isolate strategy cuts sub-agent error rates by 31% on multi-step tasks. Concrete ii-agent application: apply isolate between LBO modules — each sub-agent gets a context window with only its inputs; no module should see another module's working notes. Apply select to deal_memory: fetch only the tagged slice relevant to the current module at dispatch time, not the full deal context at session start.
Durable state + checkpoint pattern — LangGraph 1.0 formalises what ii-agent multi-day cases need consider
LangGraph 1.0's durable execution model (automatic state persistence, save/resume at any point) directly addresses the most fragile part of multi-day LBO work: losing model context mid-case when a session restarts. The pattern is: checkpoint after each validated module (Sources & Uses done ✓, Operating Model done ✓), and resume from the last clean checkpoint on the next session. This already exists informally in how ii-agent case folders accumulate Excel sheets — making the checkpoint explicit and resumable is the upgrade. Worth exploring whether the LangGraph durable state API can replace the current "re-read all prior outputs at session start" pattern.
Multi-agent orchestration: P2 dispatch contract — explicit task boundaries cut cross-module contamination
Multi-agent production research consistently identifies one fix for sub-agent failures: the P2 contract. Every sub-agent dispatch must include four elements: (1) objective, (2) output format, (3) tool/source guidance, and (4) explicit task boundary — what the sub-agent should not do. Teams that omit the boundary condition see hallucinated assumptions bleeding across modules. For ii-agent's LBO orchestrator: add a NOT-DO clause to every module dispatch. Revenue Build example: "Do not model debt schedule, capital structure, or exit assumptions — those are handled by separate agents." The boundary is as important as the objective.

Add P2 task boundary clause to all LBO module dispatch prompts quick win
The P2 dispatch contract (objective + output format + tool guidance + task boundary) is a 5-minute fix to the orchestration layer. For each module in the LBO case orchestrator, add one NOT-DO clause to the dispatch prompt. Example additions: Revenue Build → "Do not model debt or working capital"; Debt Schedule → "Do not calculate returns or sensitivity tables"; Working Capital → "Use Operating Model revenue assumptions as inputs, do not re-derive them." This prevents cross-module contamination without requiring architectural changes. Start with the modules where assumption bleed is most common: Revenue Build, Debt Schedule, and Returns Analysis.
Explore LangGraph durable state for multi-day LBO case context persistence evaluate
