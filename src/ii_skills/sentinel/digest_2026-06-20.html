02  MCP
Enterprise-Managed Authorization goes stable — zero-touch OAuth for MCP connectors via Okta (June 18)
Anthropic and Okta launched Enterprise-Managed Authorization (EMA) for Claude's MCP connectors on June 18. Built on the IETF RFC 9207 cross-app access pattern (formalized in the MCP spec in November 2025), EMA lets IT admins provision every approved MCP tool once through their identity provider and push access to every employee on first login — no per-user OAuth consent screens, no IT tickets. Seven providers support EMA at launch: Asana, Atlassian, Canva, Figma, Granola, Linear, and Supabase. The MCP protocol blog declares this "the single largest obstacle to enterprise-scale MCP adoption removed." Available in beta for Team and Enterprise plans. The broader implication: the MCP authorization layer is now an IT-governed, centrally auditable system — the same pattern that made OAuth2 safe for enterprise SaaS in 2014.

05  MCP
MCP 2026-07-28 RC locks stateless protocol — handle-as-argument pattern, MCP Apps, July 28 final spec
The largest MCP revision since launch is now a release candidate. Core change: the initialize handshake and Mcp-Session-Id header are eliminated. Every request is fully self-contained — remote MCP servers can run behind plain round-robin load balancers with zero sticky sessions. State that used to live in a session (browser handles, spreadsheet IDs, search contexts) is now an explicit argument in every tool call — visible, auditable, composable. New features in the RC: routable headers (Mcp-Method, Mcp-Name) for gateway routing without body inspection; Tasks extension for long-running work via handles; MCP Apps — server-rendered HTML UIs surfaced inside the MCP client. The MCP ecosystem now spans 15,930+ indexed servers across four registries (PulseMCP, Smithery, Anthropic, custom). Final spec ships July 28. Migration window: 10 weeks from May 21.
Architecture Watch
Context Engineering is 2026's primary discipline — the paradigm shift is now formalized read this
A paper titled "Context Engineering: A Practitioner Methodology for Structured Human-AI Collaboration" (arXiv 2604.04258) formalizes the shift from prompt engineering to context engineering. Three-stage historical arc: Prompt Engineering (2022) → Context Engineering (2024) → Harness Engineering (2026). LangChain's formal taxonomy breaks context strategies into four primitives: write (author instructions), select (choose relevant context), compress (reduce token waste), and isolate (keep unrelated context separate). For ii-agent, this validates a specific architectural choice: don't inject all of deal_memory at session start. Pull the relevant deal slice just before each module is dispatched. The 1M context window doesn't eliminate the need for context discipline — it raises the stakes of getting it wrong.
Stateless MCP is the "handle as argument" pattern at protocol level architecture
The 2026-07-28 RC enforces a clean design principle that ii-agent's skill architecture already follows: every resource (Excel workbook, PDF, deal context) is a file path argument, not a shared session object. The MCP spec is now mandating this pattern at the protocol level. Any future ii-agent skill that exposes an MCP server interface should be designed stateless-first: the skill receives all inputs as explicit arguments, executes, returns a result, and holds no session state. This is already true of pdf_extractor, excel_modules.py, and the slide generators — the pattern is correct, just make it explicit in the skill manifests.
Production agent stack is consolidating: 3 SDK targets emerge strategic
With Microsoft Agent Framework 1.0 shipping, OpenAI retiring Agent Builder, and Google ADK available in Python, Java, and Go with A2A support, the production agent framework landscape has consolidated to three serious targets: Claude Agent SDK (Anthropic-native, best for Claude-heavy workflows), Microsoft Agent Framework 1.0 (best for Azure/enterprise, .NET-first), and Google ADK (best for Gemini and multi-model A2A scenarios). LangGraph remains the deployment-share leader at 40% of production deployments. For ii-agent, this means the Claude Agent SDK is the natural host for advanced multi-agent orchestration — the 5-level nested sub-agent depth shipped last week maps directly to a Claude Agent SDK session hierarchy.
Adaptive Intent Graphs replacing linear flowcharts — the end of hardcoded orchestration
The industry is pivoting from static "map every step" orchestration to goal-declaration with dynamic routing. In the new model: you declare the ultimate goal and provide specialized agents with tools; when an agent hits an error, it communicates with a planning agent to find an alternative route (self-healing). Microsoft's retail deployment case study moved from a modular monolith where every path was pre-coded to a microservices model where domain agents become independent services that coordinators route between dynamically. For ii-agent, this suggests the next architecture evolution: replace the current sequential skill-dispatch pattern with a goal-level prompt to a coordinator agent that selects and sequences modules based on what the case actually requires.

Workflow Ideas
Add fallbackModel to Claude Code settings before the next newsletter run do this now
The Fable 5 suspension is a live example of why model fallbacks matter. With Fable 5 unavailable, any session that hard-codes Fable 5 as the primary silently fails. The fallbackModel setting (added in v2.1.166, June 6) fixes this. In ~/.claude/settings.json or your project settings, add:

"fallbackModel": ["claude-opus-4-8", "claude-haiku-4-5-20251001"]

This protects all three automated newsletter runners (networth, market, health) from silent failures when the primary quota is exhausted or the model is temporarily unavailable. The ordered chain — Opus 4.8 → Haiku 4.5 — ensures the newsletters run even in degraded conditions.
Wire post-session hook to archive Tier 3 outputs automatically build this
Added in v2.1.169 (June 8), the post-session lifecycle hook runs a shell command after a session ends before workspace deletion. This is the missing automation link between Claude Code's ephemeral workspace and ii-agent's persistent Tier 3 case folders. A two-line hook script: (1) copy output/cases/ to a stable archive path; (2) log the session ID and timestamp. Wire this in .claude/settings.json under the hooks.post-session key. No more "where did that file go after the session ended?" for complex case outputs.
Apply context engineering's "just-in-time retrieval" to deal_memory injection refine
Current pattern: inject all deal_memory at session start. Context engineering best practice: fetch the relevant deal slice at each decision point, not at session start. In practice: when the case orchestrator dispatches the Revenue Build module, it should call deal_memory.recall(deal_id, tags=["revenue", "segment", "top-line"]) just before that sub-agent starts — not load the full deal context at the top of the session. This keeps the working context lean for each sub-agent and avoids diluting attention across unrelated deal facts. The deal_memory skill's 10-action interface already supports tagged recall — it just needs to be called at dispatch time, not session-start time.
Use Claude Design beta to prototype the next IB Toolkit slide before writing python-pptx code
Before writing the next slide module in slide_modules.py, open Claude Design, describe the slide layout (e.g., "SOTP waterfall with 5 segments, value labels, and a 'total EV' callout"), let the design tool produce a visual prototype, then use /design to hand it to Claude Code. Compare the generated layout code to the python-pptx approach in slide_modules.py. If the design-first path is faster for visual refinement, it becomes the new spec process for the CFA Visual Slides (which currently rely on ASCII diagrams for layout specification — a known weak point in the SLIDE_LIBRARY.md).

⚡ This Week's Recommendation
Add fallbackModel to settings and wire the post-session hook — both take under 10 minutes
The Fable 5 suspension exposed a gap: automated session runners have no fallback when the primary model is unavailable. The fix is already in Claude Code — it just needs to be configured. Do both of these now while the context is fresh:

1. Add fallbackModel (2 minutes)
In ~/.claude/settings.json, add this line inside the top-level object:
"fallbackModel": ["claude-opus-4-8", "claude-haiku-4-5-20251001"]
This protects all three newsletter runners and any future scheduled sessions from silent model failures.

2. Wire the post-session hook (5 minutes)
Create .claude/hooks/post-session.sh with:
#!/bin/bash
cp -r output/cases/ ~/ii-agent-archive/cases/$(date +%Y-%m-%d_%H%M%S)/ 2>/dev/null || true
Then in .claude/settings.json, add:
"hooks": { "post-session": ".claude/hooks/post-session.sh" }

Both changes are reversible, have no external dependencies, and immediately improve ii-agent's resilience. The fallbackModel config especially: if Fable 5 is restored and suspended again (a real possibility given the ongoing negotiations), you want automated runs to degrade gracefully, not fail silently.
